# 01 架构与数据流

## 总体架构

```
┌─────────────────────────── MovieClaw 宿主 ───────────────────────────┐
│                                                                      │
│  ┌─ 调度器（现成）────────────────────────────────────────────┐    │
│  │ scheduled_task 表 ← 用户可改周期                              │    │
│  │   ↓ 到点触发                                                   │    │
│  └───┬──────────────────────────────────────────────────────────┘    │
│      │                                                               │
│      │ pt-keepalive:run（插件贡献的 SCHEDULED_TASKS 任务）            │
│      ▼                                                               │
│  ┌─ 插件进程（runtime=process，独立低权限）─────────────────────┐    │
│  │                                                               │    │
│  │  站点清单 = HOST_OPS site.list（已配置站点+验证状态）          │    │
│  │  展示名 = HOST_OPS site.catalog                                │    │
│  │        ↓                                                       │    │
│  │  对每个启用保活的站点：                                        │    │
│  │    ① 取适配器（sites/ 分发表按 site_id + auth_type）          │    │
│  │    ② 适配器产出步骤：代请求（method/path/headers）+ 判定函数   │    │
│  │    ③ ── HOST_OPS site.proxy.request ──────────────┐           │    │
│  │        （宿主用**自己的已认证会话**执行，回传响应） │           │    │
│  │    ④ 判定：签到成功/仅登录在线/失败/需人工/跳过     │           │    │
│  │    ⑤ 结果写 PLUGIN_DATA（每站状态机）               │           │    │
│  │    ⑥ 汇总 → PLUGIN_EVENTS.publish                   │           │    │
│  │        （失效告警/连续失败/日报）                    │           │    │
│  └────────────────────────────────────────────────────┼───────────┘    │
│                                                       │               │
│  ┌─ 站点访问层（现成）────────────────────────────────▼──────────┐    │
│  │ SiteAccessManager.get(site_id) → 已认证 BaseSite             │    │
│  │   （凭据 ACTIVE 才给；1800s TTL；自动重认证；每站限流 3s+抖动）│    │
│  │   HttpClient(site_id) → egress_transport("site:<id>")        │    │
│  │   （用户给 site:mteam 配的代理自动生效）                        │    │
│  └───────────────────────────────────────────────────────────────┘   │
│                                                                      │
│  ┌─ 推送（现成）────────────────────────────────────────────────┐   │
│  │ PLUGIN_EVENTS.publish → 系统事件总线 → 偏好筛选                │   │
│  │   → APNs / IM 通道（telegram/discord/feishu/weixin 全插件贡献）│   │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

关键分工：**插件只有「决策」，宿主才有「会话」**（M-Team 是唯一例外）。NexusPHP 站的请求
由插件把「想对这个站发什么请求」翻译成结构化计划，经宿主操作 `site.proxy.request` 执行，
拿回的只是响应（状态码/响应头子集/正文文本）——插件接触不到它们的凭据。

**M-Team 例外**：它的保活接口只认网页会话，宿主的 API Key 调它一律 401（2026-10-20 实测）。
这一站由插件用设置里保存的账号密码 + TOTP 登录（凭据进插件设置、SecretStr 加密），
会话（JWT + 设备指纹）存插件数据跨轮复用；请求直连 `api.m-team.io`（清单 `network = true`）。

## 三条动作流

### A. 保活（访问续期）— NexusPHP 系通用

- **谁需要**：Cookie 型登录的 NexusPHP 站。宿主 torrent_sync 已周期访问，但只在
  「用户配了该站做订阅/刷流」时节奏密集；保活插件对启用站点每天一次「确认性访问」。
- **动作**：GET 站点首页 → 结果判定的「登录证据」检查（页面可见文本出现 logout 链接 =
  在线；出现密码框 = Cookie 失效；Cloudflare challenge 特征 = 需人工）。
- **宿主重合说明**：这条流不改变宿主行为，是「额外一道确认 + 统一汇报」。

### B. 签到 — NexusPHP 站 + 游戏化站

### B. 签到 — NexusPHP 站 + 游戏化站

- **动作**：先 GET `index.php` 确认登录态（登出链接 = 在线，密码框 = 失效），再 GET
  `/attendance.php`（标准 NexusPHP 签到页）→ 证据判定：
  - 「这是您的第 N 次签到 / 已连续签到 N 天 / 签到已得 N 魔力」→ 签到成功；
  - 「今天已经签到过了」→ 签到成功（幂等）；
  - 页面仍出现「立即签到」按钮 → 签到未确认（降级为「仅登录成功」）；
  - 出现登录框 → Cookie 失效（走告警流）；
  - 签到页 404（站点没有这个页面）→ 登录在线，**不算失败**。
- **范围控制**：签到动作整体可开关（用户决策 #2）；关掉后只访问首页确认登录态。
- **边界**：`bakatest.php` 答题站、需验证码的签到 → 判「需人工处理」，不发请求，不算失败。

### C. 触碰（最后活跃时间）— M-Team 专用

> **2026-10-20 修正**：下面的「借宿主会话」不成立——`updateLastBrowse` 只认网页会话，
> 拿宿主的 API Key 调一律 401。现在这一站由插件用**账号密码 + TOTP** 自己登录
> （与 `scjtqs2/mtlogin` 同一路线），详见 [03-plugin.md](03-plugin.md) 的「M-Team 自登录」。

- **谁需要**：按「最后活跃时间」清理账号的站（M-Team 是实证）。宿主现有动作不覆盖：
  torrent_sync 只拉种子列表（API 站走 /api/torrent/search），不更新「最后浏览」。
- **动作**（M-Team）：`POST /api/login`（账号 + 密码 + 空 turnstile，`code 1001` 时带
  `otpCode` 再发）→ 取响应头 JWT/Did → `POST /api/member/profile` →
  `POST /api/member/updateLastBrowse`。每个请求带 `_timestamp` + `_sgin` 签名（密钥来自
  站点前端 JS，要落在插件里）。
- **判据**：`{code:"1","message":"FAIL"}` 是「站点认为无需刷新」（不是成功、也不是失效）→
  记登录在线；`code 401` / 密码错 / 账号不存在 = 凭据失效；「簽名錯誤」= 前端密钥轮换；
  「請求過於頻繁」= 限流。
- **请求头**：插件自己伪造官方前端（`Did` / `visitorid` / `version` / `webversion` / `Ts`），
  `Did` 跟站点下发值滚动，`visitorid` 永久复用。
- **频率**：默认每天 1 次即可（mtlogin 的每 2 小时是它的自愈节奏；JWT 30 天有效，
  插件缓存令牌、401 才重登）。

## 事件与通知

插件自己发的事件（清单 `[[events]]`，名字以 `pt-keepalive.` 开头）：

| 事件 | 触发 | 通知（`[[notifications]]`） | 默认 |
|---|---|---|---|
| `pt-keepalive.auth.expired` | 任一站点判定凭据失效（密码框/401/授权失败） | 「{site_name} 登录已失效」/「请在 设置→站点 更新该站凭据」 | 开（level=active） |
| `pt-keepalive.report.daily` | 每轮跑完汇总（`daily_report` 开） | 「PT 保活日报：N 站在线」+ `{detail}` | 关（level=passive） |
| `pt-keepalive.report.failures` | 有站点连续 3 轮失败，每段失败只报一次 | 「有站点连续失败」+ `{detail}` | 开（level=active） |

- 失败升级单独一条事件：日报默认关闭，不能靠它兜底，否则关掉日报的用户永远看不到失败。
- 失效告警去重：同一站点从「有告警」到「再次成功」期间只发一次（状态机记 `alerted_expired` 位）。
- Cookie 失效恢复后（用户更新凭据、`site.verify` 通过）自动清零失败计数——插件下一轮
  读 `site.list` 看到 `usable=true` 即恢复正常。

## 失败路径与安全网

| 故障 | 行为 |
|---|---|
| `site.proxy.request` 报「站点未配置 / 已停用 / 尚未验证通过」 | 该站本轮没访问，状态机记 `skipped`，不计数、不告警 |
| `site.proxy.request` 报「认证失败」 | 判凭据失效，发一次告警（告警发送失败下一轮重试） |
| 请求超时/网络错误/5xx | 单站本轮失败，**不重试**（下一轮再说）；连续 3 轮失败 → 连续失败通知 |
| Cloudflare challenge / 验证码特征 / HTTP 401 403 被 WAF 拦 | 判「需人工处理」，不计数、不熔断；不进失败统计 |
| 适配器抛异常（站点改版、选择器失效） | 单站失败记日志（ctx.logger + 关键 site_id），其余站点继续 |
| 签到请求发出但判据不认识响应 | 保守判「未确认」→ 降级「仅登录成功」，绝不虚报签到成功 |
| 未适配的纯 API 站（sunnypt） | 不发请求，记 `skipped`，不进失败统计 |
| 插件自身崩溃 | 宿主进程模型兜底：只影响本插件，自动回滚机制（版本）不受影响；定时任务下一 tick 照常触发 |
| SITE_PROXY 未授权/宿主版本旧不支持该操作 | 插件启动自检报「宿主不支持，需升级宿主」，不注册任务、不发请求 |
| 卸载 | 定时任务自动撤下（SCHEDULED_TASKS 注册表机制）；PLUGIN_DATA 默认保留（卸载不 purge） |

## 数据流小结（一次保活轮）

1. 调度器到点 → 调 `pt-keepalive.run` 处理器；
2. 插件 `site.list` 拿启用站点（usable 状态 + auth_type），`site.catalog` 补展示名；
3. 逐站（串行，宿主每站限流 3s+ 托底）：适配器 → 步骤（代请求 + 判定）→ `site.proxy.request`；
4. 状态机更新（PLUGIN_DATA，只存非敏感摘要）；
5. 汇总：有失效 → 发 `auth.expired`；有连续失败 → 发 `report.failures`；日报开关开着 → 发 `report.daily`；
6. 全程日志（ctx.logger，中文，带 site_id），诊断页可查。
