# Trakt 观看时间：分钟精度与重看边界

时间契约核查日期：2026-10-27。适用于 0.3.0；宿主兼容基线已更新为正式 MovieClaw v0.44.0。

## 官方契约

[Trakt 官方公告 #694](https://github.com/trakt/trakt-api/discussions/694) 于 2026-01-29 宣布：所有读取、写入 `watched_at` 的接口将秒与毫秒归零，计划于 3 月 1 日完成。2026-02-06 官方回复确认以 `item + watched_at` 去重。因此不能再承诺远端保存源记录的秒／微秒，也不能把同一项目、同一分钟的多次观看当作多个可区分的远端事实。

按 UTC 分钟向下截断，不是四舍五入，也不是前后 60 秒容差。例如 `2020-01-01T04:34:59.999-08:00` 对应远端 `2020-01-01T12:34:00Z`；下一分钟是不同观看，不能误判为已存在。

## 插件行为

- **MovieClaw → Trakt：** 本地源记录、排序、截止时间、幂等源 ID 和用户操作先后关系继续保留原精度。仅在 Trakt 写入及远端查重边界按 UTC 分钟处理，不写回修改 MovieClaw 数据。
- **Trakt → MovieClaw：** 保存 API 实际返回的时间。当前契约通常只提供到分钟；插件不能补回 Trakt 已丢弃的秒／微秒。它不额外截断导入响应，也不伪造秒数。
- **重看：** 同一电影或单集在不同 UTC 分钟的观看分别处理。当前本地扫描中同一分钟的额外源记录在预览中提示；第一条成功对齐后，其余列为“跳过：Trakt 按分钟合并”，不冒充全部无损成功。本地所有源记录保持原样。
- **增量：** 已有成功回执仍不重新查询或推送。当前本地目录中仍存在的已同步源记录也参与同分钟冲突检查；新增同分钟额外记录会显示跳过，合并回执避免以后重复推送。若本地已删除旧源、或历史来自其他应用，单凭一个远端分钟无法反推观看次数；“匹配”只表示分钟级对齐。
- **响应丢失／重试：** 先在目标 UTC 分钟范围分页核查同一电影／单集，存在即不重复 POST。过滤结束点即使包含下一分钟，也必须通过精确分钟相等检查。保留重复分页保护、限流退避和原有不确定写入检查点。
- **手动已看与播放补传：** 使用相同的分钟边界；本地取消已看截止时间及新旧事件排序继续使用原时间，避免一分钟内先后操作顺序丢失。
- **导出与取消已看的先后关系：** 成功对齐的历史导出先保存成员／绑定／影片或单集范围的观看标记，再提交成功回执。旧回执和来源别名恢复也补齐该标记，使用首次导出的原始时间，不采用 Trakt 归零时间或后来的目录停止时间。晚到的旧取消事件因此不会删除较新的已导出观看，真正较新的取消仍正常发送。
- **原生实时 scrobble 是另一种时间来源：** `/scrobble/stop` 只发送项目和进度，观看时间由 Trakt 在处理请求时分配，可能跨到源完成事件的下一分钟。插件在授权刷新后、每次真正派发前持久保存该项目的请求窗口；收到结果／网络错误时收窄到实际结束时刻，恢复时只匹配这个窗口中的 UTC 分钟。进程突然退出、无法保存结束时刻时使用预存的发送后 60 秒保守窗口，不把后来整个退避期间都当作同一次观看。
- **不同写入方式不能混用：** 原生 scrobble 未找到匹配而改为显式历史补传时，先持久清除派发窗口、保存源分钟写入意图，再 POST；后续不确定结果继续按源分钟查重。400／429 等确定拒绝不保留原生窗口。元数据身份变化后，旧项目的窗口不用于新项目。
- **401 与授权刷新分开：** 原生播放请求明确被 401 拒绝后，先持久清除该次派发窗口，再请求刷新令牌。刷新请求的响应丢失或 5xx 不代表被拒绝的播放可能成功；只有刷新成功、真正重发播放前才建立新窗口。测试也覆盖清除后在刷新过程中进程退出。

这不是两端事务。外部删除、并发更改、宿主没有保留的观看事实仍不能凭空恢复；原有回执也不会主动覆盖用户后来的远端删除。

原生请求的服务端接收时间没有稳定幂等 ID 可对账；同一窗口内其他来源的同项目观看也无法证明属于哪次请求。异常时钟偏差、超出保守窗口的服务端延迟仍是边界，不承诺绝对 exactly-once。显式历史导出／补传不采用这样的宽窗口。

## 验证性质

0.3.0 使用上游 #1063 的 `watch_source_ids`／目录 `source_ids`，以共同日志 ID 把实时成功投递与后续导出关联。不会拿秒差、相邻分钟或后来的停止时间猜测身份；共同回执涵盖续播的多条日志，保存于成员／绑定代次作用域，并检查媒体身份。没有共同 ID 的升级前成功记录无法自动补回这种来源关系。此版本需要正式 v0.44.0 的事件 1.1 契约，不适配只有 1.0 的 v0.43.0。

历史导出查证／写入前还会保存已确认任务的来源与原定分钟。若导出响应或回执丢失，晚到的原生完成事件先按该分钟核对，必要时沿用同一个显式历史写入意图，不另发原生 stop。共享回执保留首次导出的分钟和归属，目录别名／最终停止时间变化后，仍可正确展示同分钟额外观看的合并跳过结果。

官方契约来自上述公开公告。隔离测试使用独立实现的“分钟归零服务”模拟 Trakt，覆盖查询范围、相邻分钟、响应已提交但返回 503、进程恢复及同分钟额外记录，不使用生产凭据。真实官方 v0.43.0 SQLite／HTTP 集成另验证导出请求按分钟发送，而原生 PlaybackLog 和 PlaybackState 的秒／微秒未变；单集导入保存模拟 API 返回的分钟时间。

这证明插件符合所建模的官方契约，**不等于本候选版已经完成真实 Trakt 写入验收**。本轮没有真实账号写入、生产部署、PR 合并或公开发布。测试结果与候选包见 [本轮验证](https://github.com/o1xhack/movieclaw-trakt/blob/feat/foreground-history-sync/docs/validation-2026-10-27-minutes.md)。
